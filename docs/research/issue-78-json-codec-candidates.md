# Maintained Java 25 JSON codec candidates for BS2BG

Research for [Research maintained Java 25 JSON codec candidates](https://github.com/evildarkarchon/BS2BG/issues/78), verified against primary sources on 2026-08-28. This is a compatibility characterization, not a codec selection.

## Executive summary

Five maintained codec families remain technically usable on the Java 25, non-modular `jpackage` route, provided BS2BG owns a streaming adapter instead of binding the domain model or parsing Projects into an ordinary JSON-object map:

- Jackson Core 3.x/2.x streaming API;
- Gson 2.14 streaming API;
- Jakarta JSON Processing 2.1 with Eclipse Parsson 1.1.9;
- Moshi 1.15.2 streaming API; and
- Fastjson2 2.0.63 low-level `JSONReader`/`JSONWriter`, conditionally on closing its strict-JSON validation gap.

The decisive constraint is unusual but already accepted: a `.jbs2bg` `MorphedNPCs` object may contain repeated display-name members when the NPC Morph Assignments have different plugin/editor-ID identities. The current loader intentionally iterates every member and validates identity separately ([ProjectFileLoader](https://github.com/evildarkarchon/BS2BG/blob/ee2bb8576f57ce0608a6ed9dd7966852d9a03158/src/com/asdasfa/jbs2bg/project/ProjectFileLoader.java#L431-L474)). A normal map/tree parse either rejects or overwrites those members. Every viable replacement therefore uses the candidate's token/event reader for Project persistence, preserves repeated names only in that catalog, and performs BS2BG's duplicate and unknown-member rules itself.

The current minimal-json 0.9.5 is not a maintained candidate: upstream labels it unmaintained, and its last Central release is from December 2017 ([upstream README](https://github.com/ralfstx/minimal-json), [Central artifact](https://repo1.maven.org/maven2/com/eclipsesource/minimal-json/minimal-json/0.9.5/)). JSON-java 20260719 is actively maintained, Java 25-tested, dependency-free, and public-domain, but its `JSONObject` deliberately uses `HashMap` and its parser either rejects or overwrites duplicate keys; it cannot preserve the accepted `MorphedNPCs` shape without BS2BG effectively writing another JSON parser ([README](https://github.com/stleary/JSON-java), [`JSONObject` source](https://github.com/stleary/JSON-java/blob/20260719/src/main/java/org/json/JSONObject.java)). It is therefore not viable for the shared Project/settings/output codec role.

No candidate's default pretty-printer is itself a compatibility guarantee. BoS output needs a repository-owned canonical writer profile and byte-for-byte golden tests. This requirement does not choose a library: each viable family exposes ordered streaming writes.

## BS2BG constraints

The [accepted compatibility resolution](https://github.com/evildarkarchon/BS2BG/issues/68#issuecomment-5448586537) establishes a tolerant-reader/canonical-writer policy and fixes these JSON-specific requirements:

- `.jbs2bg` files remain unversioned and semantically compatible, not byte-identical. Root and nested Project shapes, explicit null versus synthesized missing defaults, case-insensitive identities, repeated NPC display names, recovery diagnostics, and transactional rejection must survive.
- Project JSON rejects unknown root members and malformed, unsupported, duplicate, or ambiguous data. The current schema validator rejects unknown and exactly repeated fields inside structured values ([`validateSupportedMembers`](https://github.com/evildarkarchon/BS2BG/blob/ee2bb8576f57ce0608a6ed9dd7966852d9a03158/src/com/asdasfa/jbs2bg/project/ProjectFileLoader.java#L276-L294)).
- Project integers are currently accepted through minimal-json `asInt()`, while nullable endpoints distinguish a missing member, JSON `null`, and an integer ([loader helpers](https://github.com/evildarkarchon/BS2BG/blob/ee2bb8576f57ce0608a6ed9dd7966852d9a03158/src/com/asdasfa/jbs2bg/project/ProjectFileLoader.java#L137-L205)). A replacement must not silently coerce decimals, exponents, overflow, booleans, strings, or nulls.
- Project writing is UTF-8 and atomic. Member order and whitespace are not Project contracts, but omission of unchanged synthesized defaults and emitted null members are semantic contracts ([ProjectFileWriter](https://github.com/evildarkarchon/BS2BG/blob/ee2bb8576f57ce0608a6ed9dd7966852d9a03158/src/com/asdasfa/jbs2bg/project/ProjectFileWriter.java#L145-L215)).
- `settings.json` and `settings_UUNP.json` retain their schemas, defaults, multipliers, inversion behavior, and output effects; malformed configuration must be rejected with a file/member diagnostic and never partially consumed. The present implementation parses objects into mutable global maps and uses defaulted float accessors, so the modernization must stage and validate a complete candidate before publication ([Settings](https://github.com/evildarkarchon/BS2BG/blob/ee2bb8576f57ce0608a6ed9dd7966852d9a03158/src/com/asdasfa/jbs2bg/data/Settings.java#L212-L289)).
- BoS JSON is byte-frozen for valid input: UTF-8 without BOM, minimal-json-style pretty bytes, numbered member order, all `highvalueN` members before all `lowvalueN` members, float rendering, and no accidental narrowing by UI selection. The formatter currently constructs those objects in the required order ([ProjectOutputFormatter](https://github.com/evildarkarchon/BS2BG/blob/ee2bb8576f57ce0608a6ed9dd7966852d9a03158/src/com/asdasfa/jbs2bg/presentation/ProjectOutputFormatter.java#L90-L123)).
- The build remains a classpath/non-modular application first. A dependency containing `module-info.class` is still usable from the unnamed module; the packaging question is its complete runtime closure and service discovery, not whether the JAR has a module descriptor.

## Detailed candidate evidence and compatibility implications

### Jackson Core

Jackson Core is the smallest Jackson shape that meets the requirement: it is a pull parser plus generator, not an object binder. Upstream lists Jackson 3.1 and 2.21 as open LTS branches and 3.2/2.22 as current release branches; the core README states that 3.x requires Java 17, has no external consumer dependencies, and publishes a proper Java module ([release policy](https://github.com/FasterXML/jackson/wiki/Jackson-Releases), [core compatibility](https://github.com/FasterXML/jackson-core#compatibility)). Java 25 therefore sits inside the supported runtime range.

The adapter cannot simply turn on global strict duplicate detection: that would correctly catch repeated structured fields but incorrectly reject repeated NPC display names. Manual name sets are required in all candidates, so Jackson's feature is useful for settings-only readers or tests, not the Project reader as a whole. Parser/generator constraints should be pinned to reject excessive depth, document size, and number/string lengths.

### Gson

Gson 2.14 has the closest high-level tree API to minimal-json, including insertion-ordered `JsonObject`, explicit `JsonNull`, and configurable pretty output. That superficial similarity is dangerous for Project reads: `JsonObject.add` delegates to a map `put`, so repeated display names collapse. The correct shape is a manual `JsonReader` adapter configured with `Strictness.STRICT`. This also avoids reflective binding to immutable Project snapshots and prevents unknown Java fields from silently becoming persistence schema.

Gson's main diagnostic advantage over Moshi is that syntax/type messages include line, column, and JSONPath. Its disadvantage is that only the path is a public accessor; BS2BG should not parse exception prose into a stable contract. Record a logical element path while reading and treat textual line/column as best-effort unless a small wrapper is proven reliable.

### JSON-P with Parsson

JSON-P provides the cleanest specification-owned streaming/event and location contracts. Parsson supplies the implementation and resource limits; 1.1.9 added a total parsing limit, while its API config also exposes duplicate-key rejection and depth/number limits ([Parsson configuration](https://github.com/eclipse-ee4j/parsson/blob/1.1.9/impl/src/main/java/org/eclipse/parsson/api/JsonConfig.java)). The object model is intentionally unordered, so it should not cross the BS2BG adapter boundary. The implementation's service provider and API JAR must both be included in the packaged app; a classpath smoke test should create `JsonProvider` from the installed image, not only in Maven tests.

### Moshi

Moshi's streaming API preserves field occurrences and is strict by default, so its parsing semantics are viable. It lacks a `JsonElement` model and represents generic objects as maps, reinforcing that Project decoding must be manual. Error paths are useful, but there is no line/column source location contract.

The stable artifact is materially older than the other candidates and brings Okio plus Kotlin runtime artifacts into a Java application. The active 2.0 line was alpha as of the research date and converted the implementation from Java to Kotlin while claiming binary compatibility for 1.x users ([2.0 upgrade notes](https://github.com/square/moshi/blob/master/CHANGELOG.md#200-alpha1---2026-01-28)). Those are lifecycle and packaging considerations, not semantic disqualifiers.

### Fastjson2

Fastjson2's low-level reader and writer can implement the same streaming adapter, and its ordered `JSONObject`, duplicate-combining feature, numeric APIs, offset reporting, one-JAR core, and JDK 25 CI make it a real candidate rather than a name-only comparator. The adapter must use only the low-level JSON surface: do not enable `SupportAutoType`, `SupportClassForName`, smart matching, bean binding, class-name writing, or global mutable formatting settings.

The open condition is syntax acceptance. Upstream documents that Fastjson2 rejects arbitrary commas but accepts comments and single quotes by default; `DisableSingleQuote` closes only one gap. minimal-json and the accepted malformed-input boundary do not authorize JSON-with-comments. A bounded probe must either identify a supported strict reader configuration that rejects both or specify a small, independently tested lexical preflight. Without that evidence Fastjson2 remains conditional, not rejected.

### Current and rejected comparators

minimal-json preserves duplicate object members because its `JsonObject` stores parallel name/value lists and iteration visits every member ([0.9.5 source](https://github.com/ralfstx/minimal-json/blob/0.9.5/com.eclipsesource.json/src/main/java/com/eclipsesource/json/JsonObject.java)). That behavior explains why the legal duplicate NPC display names work today and must be tested explicitly during replacement. Its MIT license, no-dependency JAR, ordered writer, and `ParseException` location are otherwise a good behavioral baseline, but upstream's unmaintained declaration fails this ticket's maintenance criterion.

JSON-java 20260719 has fresh security maintenance, no external dependencies, public-domain terms, Java 25 testing, duplicate-key rejection by default, and errors that include index/character/line ([release history](https://github.com/stleary/JSON-java/blob/master/docs/RELEASES.md), [`JSONTokener`](https://github.com/stleary/JSON-java/blob/20260719/src/main/java/org/json/JSONTokener.java)). Its public object parser cannot preserve repeated names, `JSONObject` deliberately provides no order guarantee, and `JSONWriter` does not supply a comparable pull-parser counterpart. Rebuilding an event parser on `JSONTokener` would erase its footprint advantage and put JSON grammar maintenance into BS2BG, so it is not viable across all required surfaces.

## Compatibility risks

1. **Legal duplicate catalog keys versus illegal duplicate fields.** A global reject-duplicates switch is wrong for Projects, while a tree/map parse is lossy. Tests need both repeated display names with distinct identities (accepted) and repeated structured fields or duplicate plugin/editor-ID identity (rejected).
2. **Numeric coercion drift.** Tree/object mappers often accept `1.0`, `1e0`, strings, or overflowing values for an integer. The adapter must validate the number token/lexeme before conversion and use exact range checks. Settings floats need a decided finite/range policy before publication.
3. **Null-versus-missing drift.** The Project reader must preserve explicit `null` endpoints while separately synthesizing absent slider defaults. Generic binding defaults can erase this distinction.
4. **Unknown-member drift.** Project allowlists are per object. Settings' unknown-member policy is not fully fixed by the accepted resolution and must be made explicit; no library default should decide it.
5. **BoS byte drift.** Pretty-printer indentation, LF/CRLF, final newline, slash and Unicode escaping, negative zero, exponent spelling, and float-to-decimal conversion differ among writers. Explicit call order is necessary but not sufficient.
6. **Location drift.** Jackson and JSON-P expose structured locations; Gson and Moshi expose paths with line/column either textual or absent; Fastjson exposes offset while exceptions store prose. BS2BG's adapter must normalize path/element and carry positions when trustworthy rather than leaking library exceptions.
7. **Resource-limit drift.** Depth, token, document, and number limits differ. Pin BS2BG-owned limits and translate violations into the same diagnostic family.
8. **Packaging drift.** Gson's annotation JAR, Parsson's API/provider pair and service discovery, and Moshi's Okio/Kotlin closure must be verified in the installed `jpackage` image. A successful IDE/Maven run is insufficient.
9. **Version-line drift.** Jackson has simultaneous maintained 2.x/3.x lines; Moshi has an older stable and active alpha; Fastjson2 releases frequently. The implementation plan must pin a version and upgrade policy after, not inside, codec selection.

## Adapter contract and requirements

The codec should be hidden behind repository-owned, JavaFX-independent adapters; codec types must not appear in `ProjectSession`, snapshots, presentation values, or UI code.

### Project reader

- Consume one complete JSON document through a streaming/event reader; reject trailing data.
- Maintain a JSON-pointer-like element stack and a name set for every object.
- Reject unknown or duplicate fields at every fixed-schema object. Within `/MorphedNPCs` only, retain every repeated display-name member in source order; validate duplicates later by case-insensitive plugin/editor-ID identity.
- Require exact token kinds. Preserve explicit null separately from a missing member. Validate Project integers from their source lexeme with range-safe semantics matching the compatibility corpus.
- Accumulate recoverable missing Slider Preset references without publishing partial Project state; translate syntax, type, field, duplicate, limit, and I/O failures into `ProjectDiagnostic`/`SourceLocation`.
- Return detached immutable candidates only; the existing atomic publication boundary remains outside the codec.

### Settings reader/writer

- Parse both files into detached candidate maps/lists, validate the whole schema and every numeric value, then publish together according to the later settings-migration policy.
- Make duplicate/unknown handling explicit rather than inheriting a library default.
- Preserve insertion/order semantics where they affect generated output, while treating settings file whitespace as non-contractual.
- Report file plus member path and available line/column; never catch a codec exception and silently retain a partially cleared global map.

### Canonical writers

- Provide separate Project and BoS profiles. Project output preserves schema/omission/null semantics but need not reproduce old whitespace; BoS reproduces frozen bytes.
- Emit members by explicit domain order, never by unspecified map iteration or reflection. For BoS this means `string`, `int`, `float`; `bodyname`; numbered slider names; `slidersnumber`; all high values; then all low values.
- Pin UTF-8 without BOM, JSON newline bytes, indentation, separators, escaping, final-newline policy, and numeric spelling. Feed BoS float values through the legacy `float`/rounding path and verify the writer emits the required `Float.toString` representation.
- Reject non-finite numbers and any value that cannot be represented without semantic or byte drift.

### Verification seam

Each candidate can be evaluated against the same adapter contract without changing the domain: compatibility fixtures in, detached values/diagnostics or exact bytes out. The test matrix must include malformed syntax, trailing data, unknown fields, duplicates at every relevant depth, repeated NPC display names, explicit null/missing, integer lexical variants and boundaries, Unicode/escape cases, maximum limits, settings transactionality, and BoS golden bytes.

## Unresolved validation questions

These are implementation-selection probes, not reasons to expand the wayfinding destination:

1. Which precise legacy numeric spellings were accepted by minimal-json for Project integers and settings floats (`1`, `-0`, `1.0`, `1e0`, overflow, underflow), and which belong in the valid-input corpus?
2. Are unknown settings root/default-value members intentionally tolerated for forward compatibility, or rejected like unknown Project members?
3. What exact BoS escape corpus freezes minimal-json behavior for non-ASCII, control characters, `/`, U+2028/U+2029, surrogate pairs, `-0.0`, and exponential floats?
4. Can Fastjson2 2.0.63 reject comments through a supported reader option? If not, is an owned strict lexical preflight acceptable, and can it preserve precise offsets?
5. Which maintained Jackson line is to be pinned (3.1 LTS, current 3.2, or 2.21 LTS), and which stable Moshi line is acceptable while 2.0 remains pre-GA? These are version-policy choices after semantic probes.
6. Does the non-modular installed image include and discover every dependency/provider on a clean Windows VM, particularly Parsson's `JsonProvider` and Moshi's Kotlin/Okio closure?
7. For candidates without structured line/column APIs, is a logical JSON pointer plus source file sufficient for syntax failures, or must the adapter add a verified position-tracking layer?
