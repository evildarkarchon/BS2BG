# Java 25 and JavaFX 25 delivery toolchain

Research for “Research the supported Java 25 and JavaFX 25 delivery toolchain,” current as of 2026-08-27. This note records supported options and constraints; it does not choose the downstream release policy.

## Findings

### Baseline and patch cadence

- Java 25 is an LTS release. Oracle's support roadmap lists its GA in September 2025 and Premier Support through at least September 2030; Adoptium promises Temurin 25 availability through at least September 2031. ([Oracle roadmap](https://www.oracle.com/java/technologies/java-se-support-roadmap.html), [Adoptium support roadmap](https://adoptium.net/support/))
- JavaFX 25 is also an active LTS line. It is compiled with `--release 23`, requires JDK 23 or newer, and recommends JDK 25. Gluon currently supports Windows x64, does not provide Windows ARM64 builds, and publishes JavaFX as SDKs, JMODs, and Maven artifacts. ([OpenJFX 25 release notes](https://github.com/openjdk/jfx/blob/master/doc-files/release-notes-25.md), [Gluon JavaFX roadmap and platforms](https://gluonhq.com/products/javafx/))
- The current quarterly pair is JDK 25.0.4 (25.0.4+7 in Oracle's build) and JavaFX 25.0.4, both released 2026-07-21. Temurin subsequently published 25.0.4.1+1 on 2026-08-21. JavaFX 25.0.4 contains security fixes, and its next planned patch is 25.0.5 on 2026-10-20. ([Oracle JDK 25.0.4 release notes](https://www.oracle.com/java/technologies/javase/25-0-4-relnotes.html), [OpenJFX 25 patch notes](https://gluonhq.com/products/javafx/openjfx-25-release-notes/), [Temurin releases](https://adoptium.net/temurin/releases/?version=25))
- A stable feature baseline and a current security patch are separate concerns. `javac --release 25` fixes the language level, class-file target, and public Java SE API surface; it does not select a JDK vendor or security update. Custom-runtime maintainers are explicitly responsible for updating their runtime images. ([Maven Compiler Plugin `release` guidance](https://maven.apache.org/plugins/maven-compiler-plugin/examples/set-compiler-release.html), [`jlink` documentation](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jlink.html))
- Reproducibility therefore needs exact JavaFX dependency versions and an exact JDK vendor/full-build identity in release automation. The runtime should be rebuilt and the application/package smoke-tested after each adopted JDK or JavaFX CPU. A feature-family rule such as `[25,26)` is useful for developer toolchain selection, but by itself is not a patch policy.

### Maven build and test enforcement

- Maven Compiler Plugin supports the `maven.compiler.release` property; its current stable release is 3.15.0. Setting it to `25` is the correct compiler contract rather than combining `source` and `target`. ([compiler `release` guidance](https://maven.apache.org/plugins/maven-compiler-plugin/examples/set-compiler-release.html), [Compiler Plugin 3.15.0](https://maven.apache.org/plugins/maven-compiler-plugin/download.cgi))
- Maven Toolchains Plugin 3.3.0 can discover installed JDKs and select one by a version range such as `[25,26)`. Toolchains decouple the JDK used for compilation and tests from the JDK running Maven; Compiler, Surefire, Failsafe, Javadoc, and Exec are toolchain-aware. ([JDK discovery and selection](https://maven.apache.org/plugins/maven-toolchains-plugin/toolchains/jdk-discovery.html), [Maven toolchains guide](https://maven.apache.org/guides/mini/guide-using-toolchains))
- Surefire uses the selected build toolchain for its forked test JVM by default, so one toolchain selection can make both production compilation and tests run on JDK 25. ([Surefire toolchains](https://maven.apache.org/surefire/maven-surefire-plugin/examples/toolchains))
- The Maven Enforcer `requireJavaVersion` rule checks the JDK running Maven, not a separately selected build toolchain. It is suitable if release builds require Maven itself to run on JDK 25; it is the wrong sole guard if developers may run Maven on JDK 26 while Compiler and Surefire deliberately use a side-by-side JDK 25 toolchain. ([Enforcer `requireJavaVersion`](https://maven.apache.org/enforcer/enforcer-rules/requireJavaVersion.html))
- Maven 3.9.16 is the current supported Maven 3 release, while Maven 3.8.x and earlier are EOL. A Maven Wrapper can pin the project build independently of a workstation installation. ([Maven release history](https://maven.apache.org/docs/history), [Maven Wrapper](https://maven.apache.org/tools/wrapper/))

### Non-modular JavaFX launch

- JavaFX is not in the JDK. The `javafx.*` modules must be resolved as named modules; the supported manual launch uses `--module-path` plus `--add-modules javafx.controls,javafx.fxml`. The application itself may remain non-modular in the unnamed module. Maven can resolve the platform-specific JavaFX artifacts, and the official JavaFX Maven plugin supplies a development launcher. ([OpenJFX getting started guide](https://openjfx.io/openjfx-docs/), [`Application` API contract](https://github.com/openjdk/jfx/blob/master/modules/javafx.graphics/src/main/java/javafx/application/Application.java))
- For a class-path/fat-JAR application, OpenJFX documents a small launcher class that does **not** extend `javafx.application.Application`; that launcher delegates to the real application class. This avoids the Java launcher's special JavaFX-main-class path and is the safe main class for a non-modular packaged payload. ([OpenJFX non-modular deployment](https://openjfx.io/openjfx-docs/modular.html))
- `jpackage` directly supports non-modular applications using `--input`, `--main-jar`, and optionally `--main-class`; every JAR copied from the input directory is placed on the launcher's class path. JPMS is not a prerequisite for a self-contained native launcher. ([JDK 25 `jpackage` command](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html), [original OpenJDK `jpackage` specification](https://bugs.openjdk.org/browse/JDK-8200758))

### Windows packaging and bundled runtime

- `jpackage` can produce a testable `app-image` and Windows `exe` or `msi` installers. Packages must be built on the target platform; cross-platform installer generation is unsupported. Windows EXE/MSI generation requires WiX 3.0 or newer. ([packaging overview](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html), [`jpackage` formats](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html))
- If `--runtime-image` is omitted, `jpackage` invokes `jlink` and embeds the result. The default image strips native commands, debug information, man pages, and headers. For a non-modular app it starts with the JDK module set exposed to class-path applications; additional modules can be supplied with `--add-modules`. ([packaging overview](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html))
- JavaFX should be included as named modules in that runtime. Oracle documents either passing JavaFX JMODs on the module path and adding the needed JavaFX modules, or creating a custom runtime with `jlink` and passing it to `jpackage --runtime-image`. A JavaFX 25 runtime should use the matching platform and patch-level JMODs. ([image and runtime modifications](https://docs.oracle.com/en/java/javase/25/jpackage/image-and-runtime-modifications.html), [Gluon downloads](https://gluonhq.com/products/javafx/))
- JDK 25 distributions need not have the same on-disk shape. Temurin 25 omits the JDK `jmods` directory by default and enables JEP 493 link-from-runtime support instead. Packaging scripts must not hard-code `$JAVA_HOME/jmods`; they must exercise the selected vendor build's `jlink`/`jpackage` while still supplying the external JavaFX JMODs. ([Temurin 25 announcement](https://adoptium.net/news/2025/09/eclipse-temurin-25-available/), [OpenJDK linkable-runtime behavior](https://bugs.openjdk.org/browse/JDK-8317420))
- JDK 25 changed the default: `jpackage` no longer asks `jlink` to bind service providers. An application that relies on a provider found through `ServiceLoader` may need `--jlink-options --bind-services` together with the ordinary default stripping options. This must be verified from the final dependency graph and packaged smoke tests rather than enabled blindly. ([JDK 25 packaging overview](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html))
- The supported validation sequence is to produce and smoke-test `--type app-image` first, then turn that image into the chosen installer. The application image exposes the exact launcher configuration and bundled runtime before WiX is involved. ([basic packaging](https://docs.oracle.com/en/java/javase/25/jpackage/basic-packaging.html), [image modification workflow](https://docs.oracle.com/en/java/javase/25/jpackage/image-and-runtime-modifications.html))

### When JPMS or a separate `jlink` step is materially useful

- A modular main application lets `jpackage` link the main module and the transitive closure of its declared dependencies, producing a more precise runtime graph. JPMS additionally provides reliable configuration and strong encapsulation. A separate `jlink` step is useful when the runtime must be reused, built with different options or a different JDK than `jpackage`, or inspected independently. ([packaging overview](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html), [runtime customization](https://docs.oracle.com/en/java/javase/25/jpackage/image-and-runtime-modifications.html))
- Those benefits are not free for this repository. `jlink` does not accept automatic modules. Local inspection with `jar --describe-module` shows all three current non-JavaFX runtime libraries are automatic modules: `minimal.json` 0.9.5, `org.apache.commons.io` 2.6, and `juniversalchardet` 2.1.0. A fully modular image would therefore also require dependency upgrades/replacements or maintained modular wrappers. ([OpenJDK automatic-module limitation](https://bugs.openjdk.org/browse/JDK-8264998))
- FXML adds module-descriptor work: controller/model packages reached reflectively must be opened to `javafx.fxml`, and the application package must be exported or opened to `javafx.graphics`. Remaining non-modular avoids this migration while still allowing a trimmed JDK-plus-JavaFX runtime. ([`Application` module-access contract](https://github.com/openjdk/jfx/blob/master/modules/javafx.graphics/src/main/java/javafx/application/Application.java), [`FXMLLoader` API](https://openjfx.io/javadoc/25/javafx.fxml/javafx/fxml/FXMLLoader.html))
- JPMS is therefore materially preferable only if measured installer/runtime reduction, encapsulation, or another named-module requirement outweighs conversion of the current automatic dependencies and reflective FXML surface. It is not needed merely to use `jpackage`, bundle Java, or keep JavaFX on its supported module path.

### Licensing and redistribution

- The runtime provider is a release input because terms differ. Eclipse Temurin binaries are offered indefinitely at no cost under GPLv2 with the Classpath Exception. Oracle JDK 25 is currently under the No-Fee Terms and Conditions (NFTC), but NFTC permits redistribution of the unmodified program only when no fees are associated with the distribution, a bundled product, or a related service. Oracle plans JDK 25 NFTC updates only through September 2028; its FAQ says later OTN-licensed updates do not permit redistribution. A custom `jlink` image also warrants explicit review against the NFTC's “unmodified Program” wording. ([Adoptium FAQ](https://adoptium.net/docs/faq), [Oracle NFTC](https://www.oracle.com/downloads/licenses/no-fee-license.html), [Oracle licensing FAQ](https://www.oracle.com/java/technologies/javase/jdk-faqs.html))
- OpenJFX is GPLv2 with the Classpath Exception. The exception permits linking independent application modules and distributing the resulting executable under the application's own terms, subject to each independent module's license. It does not remove GPLv2 duties for the JavaFX components themselves; object-code distribution requires corresponding source or another Section 3-compliant offer. ([OpenJFX 25 update license](https://github.com/openjdk/jfx25u/blob/master/LICENSE), [OpenJFX additional license information](https://github.com/openjdk/jfx25u/blob/master/ADDITIONAL_LICENSE_INFO))
- Releases should pin exact JDK and JavaFX build identifiers, preserve the runtime's `legal/**` and upstream notice files, and make the exact corresponding sources available in a GPLv2-compliant way. JavaFX graphics also has module-specific native-component notices. ([Temurin 25 binary/source releases](https://github.com/adoptium/temurin25-binaries/releases), [OpenJFX 25 update sources](https://github.com/openjdk/jfx25u), [JavaFX graphics legal material](https://github.com/openjdk/jfx25u/tree/master/modules/javafx.graphics/src/main/legal))
- `jpackage` accepts a `--license-file`, but that installer metadata is not a substitute for a third-party notice/source-compliance bundle. A release must preserve the selected JDK's and JavaFX distribution's license/legal material and audit every staged dependency. This note is technical research, not legal advice. ([`jpackage` command](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html))
- “WiX 3.0 or newer” is a technical lower bound, not a version policy. WiX v3 is archived; current WiX releases have version-dependent Open Source Maintenance Fee/EULA terms, including organization-revenue conditions. Release automation must pin a reviewed major/version rather than install `latest`, and verify whether any WiX-originated material is redistributed in the final installer. ([WiX v3 archive](https://github.com/wixtoolset/wix3), [WiX Open Source Maintenance Fee](https://docs.firegiant.com/wix/osmf/), [WiX license](https://github.com/wixtoolset/wix/blob/main/LICENSE.TXT))

## Repository-specific implications

- [`pom.xml`](../../pom.xml) already pins JavaFX 25.0.4, matching the current JavaFX 25 CPU, but still sets `maven.compiler.release` to 8 and deliberately compiles only JavaFX-independent packages. The modernization build must eventually remove that include-only verification boundary, compile the whole application with release 25, and run tests through the JDK 25 toolchain.
- The repository has no `module-info.java`. [`Main.java`](../../src/com/asdasfa/jbs2bg/Main.java) extends `Application`, so a non-`Application` packaging launcher is a small, contained requirement if the non-modular route is retained.
- A supported non-modular staging shape is: the application JAR and all runtime dependency JARs in `jpackage --input`; JavaFX controls/FXML JMODs on the packaging module path; `javafx.controls,javafx.fxml` added to the bundled runtime; and a launcher main class in the application JAR. Exact JDK modules and any service binding must be validated once the full UI compiles.
- The workstation currently runs Maven 3.9.16 on Oracle JDK 26.0.2, and its JDK 26 `jpackage` is not directly on `PATH`. A JDK 25 install/toolchain is still required for repeatable Java 25 runtime construction even though JDK 26 can remain the interactive development JDK.
- Windows x64 is the only standard JavaFX 25 Windows target published and supported by Gluon. Windows ARM64 would require a custom JavaFX build or a different supported binary source and is not just another `jpackage` flag.

## Decision inputs surfaced

1. Select the release-runtime vendor and support model (for example, community Temurin versus Oracle JDK terms/support), considering whether distribution can ever be paid or bundled with a paid product/service; then pin its exact full build and legal payload.
2. Decide whether release Maven itself must run on JDK 25, or whether Maven may run on JDK 26 while a discovered side-by-side JDK 25 toolchain drives compile, tests, and packaging tools.
3. Choose Windows x64 as the supported architecture or explicitly fund a custom Windows ARM64 JavaFX supply chain.
4. Choose EXE, MSI, or both; select a reviewed WiX major/version with its support and OSMF/EULA implications, and decide installer scope/upgrades separately from Java runtime construction.
5. Retain the non-modular application initially, or justify JPMS with measured runtime-size/encapsulation value after accounting for the three automatic dependencies and FXML package openings.
6. Define the quarterly patch adoption window and the evidence required after each JDK/JavaFX runtime rebuild.
7. Determine from the completed dependency graph whether service binding is required and capture the exact JDK/JavaFX module list in a packaged-runtime smoke test.
8. Define a release-compliance gate for corresponding source, preserved `legal/**` files, third-party notices, and final installer-content inspection.

## Facts still uncertain

- The minimum supported Windows version and CPU baseline depend on the chosen JDK binary provider as well as JavaFX; neither has been selected by this ticket.
- The final JDK module closure, service-provider needs, and launcher arguments cannot be established while the Maven build excludes the JavaFX UI and before future UI libraries are selected.
- The size benefit of JPMS over the non-modular `jpackage` runtime has not been measured on a complete application.
- Code-signing identity, certificate storage, installer upgrade identity, and distribution channel remain outside this toolchain investigation.
- Exact legal notice/source-delivery steps depend on the selected JDK distribution and final dependency inventory and should be reviewed before public release.
