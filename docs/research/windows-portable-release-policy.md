# Windows portable release policy facts

Research date: 2026-08-28. Sources are first-party documentation, project source, or official artifact registries.

## First-round policy recommendation

- Publish one Windows x64 portable artifact named `BS2BG-<version>-windows-x64.zip`. Build it with `jpackage --type app-image`, preserve the generated top-level directory, and archive it without adding BS2BG Authenticode signatures. A Windows app image contains the native launcher, application files, and bundled runtime; `--type app-image` creates that directory without an installable bundle. [Oracle JDK 25 `jpackage` guide](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html) [Oracle JDK 25 tool specification](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html)
- Treat Windows 10 22H2 x64 and supported Windows 11 x64 releases as release-blocking project compatibility targets. Windows 10 support has no automatic sunset; retiring it requires a future explicit maintainer decision after judging user migration.
- Describe Windows 10 support narrowly: “BS2BG is compatibility-tested on Windows 10 22H2 x64.” Do not imply that Microsoft still generally supports Windows 10 or that Oracle certifies JDK 25 there. General Windows 10 22H2 support ended on 2025-10-14; ESU provides only enrolled systems with critical/important security updates and does not restore the ordinary lifecycle or technical support. Oracle's JDK 25 certified Windows list contains Windows 11 x64 only. Adoptium and Gluon list Windows x64 as supported for Temurin/JavaFX but do not name Windows 10 on those current pages, so Windows 10 is a BS2BG verification commitment rather than a version-specific vendor guarantee. [Microsoft Windows 10 release information](https://learn.microsoft.com/en-us/windows/release-health/release-information) [Microsoft ESU lifecycle FAQ](https://learn.microsoft.com/en-us/lifecycle/faq/extended-security-updates) [Oracle JDK 25 certified configurations](https://www.oracle.com/java/technologies/javase/products-doc-jdk25certconfig.html) [Adoptium supported platforms](https://adoptium.net/supported-platforms) [Gluon JavaFX supported platforms](https://gluonhq.com/products/javafx/)
- Exclude MSI/EXE installers, WiX, install scope, upgrade codes, repair/uninstall behavior, installed shortcuts, and installer-owned file associations from this policy; they contradict the selected portable-delivery shape.

## What `app-image` does and does not provide

The generated Windows layout is a self-contained directory containing `BS2BG.exe`, `app/`, and `runtime/`. `jpackage` can create the runtime itself with `jlink`, or copy a predefined runtime supplied through `--runtime-image`; Oracle explicitly permits modifying an app image before distribution. [Oracle JDK 25 packaging overview](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html) [Oracle JDK 25 packaging guide (PDF)](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-tool-user-guide.pdf)

JDK 25's Windows launcher normally re-executes itself after preparing its native-library environment. Set `win.norestart=true` in the generated `app/BS2BG.cfg` `[Application]` section so the original launcher process hosts the JVM, then require the packaged smoke gate to prove that it is the image's only BS2BG process, that `jvm.dll` loads from the bundled runtime, and that no observed JVM/JavaFX launcher library comes from outside the extracted image. This is an app-image post-processing step rather than a documented `jpackage` CLI option, so the pinned JDK launcher behavior and the fail-closed runtime check are both part of the release contract. [OpenJDK 25 Windows launcher source](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/jdk.jpackage/windows/native/applauncher/WinLauncher.cpp)

If `jpackage` creates the runtime, its defaults strip debug information, native commands, headers, and man pages. In JDK 25 it also omits service bindings unless `--bind-services` is passed through `--jlink-options`, so the final runtime-module and service-provider closure still needs the packaged-runtime verification already required by the modernization map. [Oracle JDK 25 tool specification](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html) [Oracle JDK 25 packaging overview](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html)

Set the authoritative application version with `--app-version`, and also use it in the Git tag, ZIP filename, displayed version, and release notes. The JDK 25 app-image test verifies that the generated launcher exposes this value as the `jpackage.app-version` system property; because there is no MSI, MSI's three-field `ProductVersion` restriction is irrelevant here. [Oracle JDK 25 tool specification](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html) [OpenJDK 25 `BasicTest.testJpackageProps`](https://github.com/openjdk/jdk/blob/jdk-25-ga/test/jdk/tools/jpackage/share/BasicTest.java)

`--file-associations` is an application-package option, not an application-image option. A portable ZIP therefore does not register `.jbs2bg`, add Start-menu or desktop shortcuts, or alter Windows uninstall state. If double-click opening is later desired, it should be a separate, explicit opt-in registration/unregistration feature or documented Windows action; it is not part of the portable artifact itself. [Oracle JDK 25 tool specification](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html)

The remaining human policy choice is settings location. `jpackage` does not decide where application settings or user data live. Its launcher can expand runtime-calculated `$APPDIR`, `$BINDIR`, and `$ROOTDIR` tokens in arguments and JVM options, so either beside-the-app storage or profile-local storage can be implemented deliberately. Decide whether “portable” means only “no installation/runtime prerequisite” or also “all settings travel with the extracted directory”; project files must remain user-chosen documents either way. [Oracle JDK 25 launcher options](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html)

## Exact runtime provisioning, build JDK, and redistribution

The accepted baseline can be provisioned without a preinstalled JDK 25. Pin these two official artifacts and fail before extraction if their SHA-256 differs:

| Eclipse Temurin 25.0.4.1+1, Windows x64 JDK | [`OpenJDK25U-jdk_x64_windows_hotspot_25.0.4.1_1.zip`](https://github.com/adoptium/temurin25-binaries/releases/download/jdk-25.0.4.1%2B1/OpenJDK25U-jdk_x64_windows_hotspot_25.0.4.1_1.zip) | `00C847D804F4A78E9F04F2683FAF14FED898535B177B7FC704486CB0284E9283` |
| Gluon JavaFX 25.0.4, Windows x64 JMODs | [`openjfx-25.0.4_windows-x64_bin-jmods.zip`](https://download2.gluonhq.com/openjfx/25.0.4/openjfx-25.0.4_windows-x64_bin-jmods.zip) | `C5471E71D3F66DB340C1E59D8B4924487AB4917AAF641FC1E4E0FA1A174F79E1` |

Adoptium publishes the Temurin checksum and signature as release assets and exposes exact-version downloads through its API. Gluon's official download page supplies the exact JMOD archive but no companion checksum link; the JavaFX value above was recorded from that official artifact on the research date. Consequently, every JavaFX update must be an explicit reviewed lock-value change, not a mutable “latest” download. [Adoptium API/reproducible-build example](https://adoptium.net/docs/reproducible-verification-builds/reproduce-windows-x64/) [Adoptium Temurin 25 releases](https://adoptium.net/temurin/releases/?version=25) [Gluon JavaFX downloads](https://gluonhq.com/products/javafx/)

A repository-owned PowerShell provisioning step can use `Invoke-WebRequest`, `Get-FileHash -Algorithm SHA256`, and `Expand-Archive` to populate a versioned build cache, then verify the extracted Temurin `java`, `javac`, `jlink`, and `jpackage` versions plus `jmod describe` on the JavaFX modules. Set process-local `JAVA_HOME` to that extracted JDK for the Maven Wrapper and pass the extracted JavaFX JMOD directory on the module path; this works identically on a clean local machine and CI and writes nothing into a global JDK installation. SHA-256 is PowerShell's default secure file-hash algorithm. [Microsoft `Get-FileHash`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/get-filehash) [Oracle JDK 25 `jpackage` runtime options](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html)

Oracle JDK 26 can run current Maven: Maven 3.9 requires JDK 8 or later, and Maven toolchains deliberately allow Maven to run on one JDK while compiler, test, and other toolchain-aware plugins use another. JDK 26's `javac --release 25` compiles with Java 25 language rules, class-file target, and documented Java 25 APIs; Oracle JDK 26.0.2's own `javac --help` lists release 25. [Maven installation requirements](https://maven.apache.org/install) [Maven toolchains guide](https://maven.apache.org/guides/mini/guide-using-toolchains.html) [Maven Compiler Plugin `--release`](https://maven.apache.org/plugins/maven-compiler-plugin/examples/set-compiler-release.html) [Oracle JDK 26 `javac`](https://docs.oracle.com/en/java/javase/26/docs/specs/man/javac.html)

That makes JDK 26 an acceptable bootstrap/Maven host, not the bundled runtime. Tests otherwise run on Maven's host JDK, and `jpackage` without `--runtime-image` uses its own JDK to create the runtime, so an unguarded JDK 26 build would silently test or bundle Java 26. Use the provisioned Temurin 25 toolchain for compilation, tests, `jlink`, and `jpackage`, or explicitly pass its runtime image. Java 26 is non-LTS and scheduled to be superseded in September 2026, whereas the map's destination is Java 25 LTS; changing the bundled runtime to 26 would reopen that destination rather than solve provisioning. [Maven toolchains guide](https://maven.apache.org/guides/mini/guide-using-toolchains.html) [Oracle JDK 25 runtime-image guide](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-tool-user-guide.pdf) [Oracle Java SE support roadmap](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)

Temurin binaries are supplied under GPLv2 with the Classpath Exception and may be used, modified, and shared under their included licenses; OpenJFX states the same license family. The Classpath Exception permits an independently licensed application to link to the covered libraries, but binary redistribution still requires preserving notices and making complete corresponding source available through a GPLv2-compliant mechanism. Put the exact runtime/component licenses and notices in the ZIP, and publish an exact source manifest plus corresponding-source downloads or same-place links with the release. This is a compliance engineering recommendation, not legal advice. [Adoptium licensing FAQ](https://adoptium.net/docs/faq) [OpenJFX licensing statement](https://openjfx.io/) [OpenJDK GPLv2 with Classpath Exception](https://openjdk.org/legal/gplv2+ce.html)

## Completely unsigned releases: consequences and integrity controls

BS2BG will add no Authenticode signature to its launcher or archive. Any signatures retained on unmodified upstream runtime files authenticate only those vendor files, not BS2BG or the ZIP.

The user-visible cost is material: Microsoft documents that unsigned direct-download applications can show “Windows protected your PC,” require the user to choose “Run anyway,” and can be blocked without a bypass by enterprise policy. Unsigned files start SmartScreen reputation from zero on every new version because no publisher identity carries reputation forward. On Windows 11, Smart App Control enforcement blocks unknown unsigned apps/binaries unless Microsoft's intelligence service already considers them safe; integrity checks cannot create that reputation or satisfy a signature-enforcement policy. Release notes must explain the expected prompt and verified download procedure, but must not instruct users to disable Defender, SmartScreen, or Smart App Control. [Microsoft SmartScreen reputation guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) [Microsoft Smart App Control overview](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview)

Compensate at the distribution layer: publish the ZIP, `SHA256SUMS`, license/source manifest, and release notes as assets on an immutable GitHub Release. Immutability locks the tag and assets and generates a release attestation; users can run `gh release verify-asset <tag> <zip>` to verify that a local ZIP exactly matches the attested asset, then independently compare `Get-FileHash -Algorithm SHA256` with `SHA256SUMS`. A checksum copied from the same compromised page is not by itself proof of publisher identity, which is why the immutable release attestation is the stronger provenance control. These controls detect replacement or corruption but cannot remove SmartScreen warnings or unblock signature-only environments. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) [GitHub release-integrity verification](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity) [Microsoft `Get-FileHash`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/get-filehash)

`jpackage` intentionally supplies no auto-update mechanism. The first release channel should therefore be stable GitHub Releases with a permanent “latest release” URL. Recommended manual update instructions are: close BS2BG, download and verify the new ZIP, extract it to a new directory rather than merging it over the old image, launch and verify the new version, then retain or remove the old directory according to the chosen settings policy. This side-by-side procedure keeps rollback possible and avoids partially mixing two self-contained images. [OpenJDK `jpackage` scope](https://bugs.openjdk.org/browse/JDK-8200758) [GitHub release links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)

Release-operations concerns remain outside application implementation: SmartScreen/reputation support, immutable-release publication, checksum/attestation retention, corresponding-source compliance, and monitoring Microsoft/JDK/JavaFX support changes. The release gate nevertheless owns full Windows 10 22H2 x64 compatibility evidence until the maintainer explicitly retires that target. The implementation specification still needs to decide settings location and whether any opt-in shell integration is worth weakening the “no system changes” portable contract.
